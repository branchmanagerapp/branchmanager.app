The verdict up front

Path: Capacitor shell + 4–5 real native features. Skip PWABuilder. PWABuilder's iOS output is a thin WKWebView wrapper — exactly what Apple's guideline 4.2 reviewers reject. Capacitor wraps the same BM code but gives a real native bridge, and every native feature we'd add maps to something BM already does on the web side, so it reads as a genuine app, not a repackaged site.

Honest advisor note [Likely]: the App Store listing matters for Branch Manager the SaaS product (credibility vs Jobber, "download our app" on the pricing page). For your own crew, the PWA already installs from Safari and does the job. This is a marketing/growth investment, not an ops need — roughly 2–4 weeks of focused work plus Apple review cycles. Fine to park until the SaaS side has pull.

⚠️ Hard constraint found: your Mac can't build this

Since April 28, 2026 Apple requires all App Store submissions to be built with Xcode 26 / iOS 26 SDK, which needs macOS Tahoe — and your Intel MacBook can't run Tahoe (same reason Palmier was a no-go). So local iOS builds are off the table.

The workaround is normal and cheap: cloud Mac builds — Codemagic (free tier ~500 min/mo), Ionic Appflow, or GitHub Actions macOS runners. Capacitor projects build fine on all three. Budget $0–40/mo. You still need an Apple Developer account: $99/yr.

Native features that earn approval (and are actually useful)

Apple explicitly says bolting on push + GPS isn't enough. The winning move: native features tied to what BM already does.

  1. Push notifications (APNs) — payment received, quote approved, new request, schedule change. BM already generates all these events server-side (Stripe webhook, quote-update, request-notify). Real utility, easy to demo to a reviewer. Must be optional, never marketing without opt-in.
  2. Native camera + photo library — job photos straight into the job-photos bucket (crew photo flow already exists; the AI-extract-uploads onboarding flow too). Native capture with offline queueing is a genuine step up from the web file input.
  3. Biometric login (Face ID) — auth gate is already a ship-blocker on the pre-ship audit; Face ID on the native shell solves mobile login friction and reads as native.
  4. Offline mode — BM's localStorage-first design is unusually close to this already; surfacing "works in the field with no signal, syncs later" is both true and reviewer-friendly.
  5. Geofenced arrival ("on my way" / auto clock-in) — geofence.js exists web-side; CoreLocation region monitoring makes it real background behavior the web can't do. Optional but the strongest "this is an app" signal.

Ship 1–4 for submission; 5 is the stretch goal.

Submission checklist (the non-code stuff that blocks approval)

  • Apple Developer Program — $99/yr, needs D-U-N-S if enrolling as the LLC (recommended for the SaaS brand).
  • Privacy policy URL — privacy.html exists; needs App-Store-specific data-collection disclosure review.
  • Privacy nutrition labels + privacy manifest (mandatory since May 2024) — declare data types, API-usage reasons, third-party SDKs (Supabase, Stripe).
  • Camera/location/notification permission strings — plain-English reasons.
  • Demo account for the reviewer — a seeded tenant with fake data (the provision-tenant flow can mint this).
  • Screenshots for 6.7" and 5.5" devices; App Store description that leads with the native features.
  • Sign in with Apple — required if any third-party login is offered; BM is email/password only today, so not required. Keep it that way for v1.
