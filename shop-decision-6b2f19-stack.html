This page exists because the answer to “what framework is it using?” turned out to be none, and that is worth writing down properly rather than re-deriving next time.

How a page actually reaches a customer

There are two separate layers doing completely different jobs, and conflating them is what makes this confusing.

Layer 1 — URL to page. This is the routing.

A Cloudflare Worker. It matches the path and hands back the matching file. /2ntr/shop/ returns one 63 KB HTML file. That is the entire routing layer.

No React Router, no Next.js, no Express, no framework. HTML pages with links between them, exactly as you described it. Verified: the bytes are identical whether you request as an iPhone or a Mac, so there is no server-side rendering — nothing is generated per visitor.

It is also why /admin, /pos and /checkout return 404 on skateos.com. No file sits there, and nothing generates one on the fly.

Layer 2 — page to products. This is not routing at all.

The page arrives in the browser with no products in it. Then its JavaScript calls the database directly over HTTPS:

https://zecurmlenxyxanqucrga.supabase.co/rest/v1/products ?select=id,name,price,image_url,brand,category_id,quantity,status &status=eq.active &order=created_at.desc

That is PostgREST — the API you could not find. Supabase generates a REST endpoint automatically for every table in the database. Nobody wrote it; it exists because the table exists. The browser talks straight to the database’s HTTP layer, and no server of yours is involved.

The sentence that resolves all of it

The page is static. Only the data is live.

When new grip tape appears on the site, no file was rebuilt, no deploy ran, nothing regenerated. A row was inserted in a table, and the next visitor’s browser asked the same question and got one more answer back. Nothing on the server is ever rewritten — it is rows, not files.

The four layers

HTML
What is on the page. Structure and content.
CSS
What it looks like. A separate language, applied to the HTML.
JavaScript
What it does. On your shop page: fetches products, draws tiles, runs filters and the cart.
React
Not used. A library that would reorganise the JavaScript in the row above. It does not replace HTML or CSS.

HTML is to CSS as JavaScript is to React. In each pair the first is the foundation and the second is a layer added on top to keep things manageable at scale. CSS with no HTML has nothing to style; React with no JavaScript does not exist.

Where the analogy breaks: CSS is a genuinely separate language — you stop writing HTML and start writing CSS. React is not like that. When you write React you are still writing JavaScript the whole time. There is no second language, just a different way of organising the first.

What React actually is

Two files. Measured, not estimated:

FileSizeJob
react.production.min.js10 KBThe component model
react-dom.production.min.js129 KBThe part that touches the page
Total140 KB 

You can drop both in with two script tags and start using it. No install, no build, no tooling. It is a library, in the same sense jQuery was.

The catch — JSX, and what it drags in

Almost nobody uses React that way, because of JSX: syntax that lets you write what looks like HTML inside JavaScript.

// JSX — a browser cannot read this return <div className="card">{product.name}</div>

It has to be compiled first into real JavaScript:

// what it becomes — this a browser can run return React.createElement('div', {className:'card'}, product.name)

That compile step is what pulls in the whole toolchain: Node, npm, a bundler, a node_modules folder, a build command, and a deploy pipeline that runs it before anything ships.

 What it isWhat it costs
React alone2 JS files, 140 KBNothing — drop it in
React as normally writtenReact + JSXA build step and a toolchain

You can write React with no build step at all by calling React.createElement directly. It works. Nobody does it, because JSX reads far better — and by the time a project wants React it usually wants the tooling too.

Why this does not change the shop page

The behaviour you asked for already exists

“Add items to the database and have them appear without touching HTML” is how that page already works — 1,409 products, none hardcoded. Plain JavaScript gets the identical result a customer would see. Rewriting it in React would change nothing visible.

And it would cost something real. The page today has no build step: one file that runs as-is. Edit it, push it, done. That is why it is 63 KB with no dependencies to break.

Adding React would not just add 140 KB — it would convert a file you can open and edit into a project that must be compiled before it can be deployed.

Where React would genuinely earn its place

Lots of interacting state across many screens — a POS holding an open ticket, split tender, a customer lookup and a cart that has to stay in sync in three places at once. That is the problem React was built for.

Not a page that fetches a list and draws tiles.

The real missing piece was never a framework

The shop page’s actual gaps are that its checkout takes no money, and that its product database shares only 30% of its names with your Square catalogue. Neither is fixed by React. Both are covered on the Architecture page.
